# NGINX HTTP/2 Bomb 漏洞（CVE-2026-49975）分析与修复指南

## 前言

2026 年 6 月，安全研究人员披露了一个影响多个主流 Web 服务软件的高危拒绝服务漏洞——CVE-2026-49975，又被称为“HTTP/2 Bomb”。

该漏洞利用 HTTP/2 协议中的头部压缩机制与流量控制机制之间的特性，使攻击者仅需发送极少量网络流量，便能够诱导服务器消耗大量内存资源，最终导致服务响应缓慢甚至崩溃。

受影响的软件包括 NGINX、Apache HTTP Server、Microsoft IIS、Envoy 等广泛部署的 Web 服务组件，因此引起了安全社区的高度关注。

---

# 什么是 CVE-2026-49975？

CVE-2026-49975 是一种远程拒绝服务（DoS）漏洞。

攻击者无需登录服务器，也无需获取任何权限，只要能够与开启 HTTP/2 的服务建立连接，就有机会触发漏洞。

漏洞信息：

- 
漏洞编号：CVE-2026-49975

- 
漏洞名称：HTTP/2 Bomb

- 
漏洞类型：拒绝服务（DoS）

- 
利用难度：低

- 
用户交互：无需

- 
攻击目标：HTTP/2 服务

与传统的大流量 DDoS 不同，该漏洞主要依靠协议层面的资源放大效应实现攻击，因此攻击成本非常低。

---

# 漏洞原理分析

为了提高网络传输效率，HTTP/2 引入了许多新特性，其中包括：

- 
HPACK Header Compression（头部压缩）

- 
Stream Multiplexing（流复用）

- 
Flow Control（流量控制）

而 HTTP/2 Bomb 正是利用了其中两项机制。

## 第一步：头部压缩放大

攻击者发送体积很小的 HTTP/2 请求。

服务器在解压 Header 时，需要创建大量内存对象。

例如：

```
客户端发送：16KB 数据

服务端解压后：
占用数百 KB 至数 MB 内存
```

攻击者发送的数据很少，但服务器需要消耗大量资源进行处理。

这就是典型的资源放大攻击。

---

## 第二步：阻止资源释放

正常情况下：

```
客户端 → 请求
服务器 → 响应
客户端 → 接收响应
服务器 → 释放资源
```

而攻击者会故意修改 HTTP/2 流量控制窗口。

```
客户端 → 不接收响应
窗口大小 → 0
```

此时服务器无法正常发送数据。

已经分配的内存也无法及时回收。

随着大量连接持续建立：

```
内存不断增长
↓
Worker进程资源耗尽
↓
系统负载飙升
↓
服务崩溃
```

最终导致拒绝服务。

# NGINX 是否受到影响？

根据公开披露的信息，部分 NGINX 版本受到影响。

主要风险集中在：

```
NGINX 1.29.8 之前版本
```

官方已经在后续版本中增加相关保护机制。

因此建议尽快升级到：

```
NGINX 1.29.8+
或更新版本
```

如果使用的是 Linux 发行版自带的软件包，则需要关注发行版的安全公告。

部分发行版虽然版本号较低，但可能已经回移植（Backport）安全补丁。

因此不能仅凭版本号判断是否存在风险。

---

# 企业和个人站长应该关注什么？

虽然 CVE-2026-49975 并不属于远程代码执行漏洞，但其实际影响依然非常严重。

因为攻击者无需占用大量带宽，就可能导致服务器资源耗尽。

对于以下场景尤其值得关注：

- 
启用了 HTTP/2 的网站

- 
使用 NGINX 作为反向代理的业务系统

- 
API 接口服务

- 
云服务器与 VPS

- 
高并发业务环境

- 
长期未更新的软件环境

服务器遭受攻击后可能出现：

- 
CPU 占用率异常升高

- 
内存持续增长

- 
网站访问缓慢

- 
API 请求超时

- 
Worker 进程异常退出

- 
OOM 导致服务中断

对于配置较低的服务器而言，风险更加明显。

```

```

输出示例：

- 
检查官方安全公告

检查发行版补丁记录

# 修复方案

## 方案一：升级 NGINX

最推荐的方法是直接升级。

例如：

```
apt update
apt upgrade nginx
```

或者：

```
dnf update nginx
```

升级后重新检查版本：

```
nginx -v
```

确保已安装包含安全修复的版本。

宝塔面板升级：

![](assets/png/articles/a481667f8f74.webp)

---

## 方案二：更新系统安全补丁

对于：

- 
Debian

- 
Ubuntu

- 
AlmaLinux

- 
Rocky Linux

- 
CentOS Stream

建议定期执行系统更新。

很多发行版会提前回移植安全补丁，而无需升级到最新主版本。

---

## 方案三：优化 HTTP/2 配置

可以适当限制客户端请求规模。

例如：

```
large_client_header_buffers 4 8k;
client_header_buffer_size 1k;
```

同时限制异常连接数量：

```
limit_conn_zone $binary_remote_addr zone=addr:10m;
limit_conn addr 20;
```

虽然无法彻底修复漏洞，但可以减少攻击面。

---

## 方案四：启用请求限速

对于高风险业务：

```
limit_req_zone $binary_remote_addr zone=req_limit:10m rate=20r/s;
```

然后：

```
limit_req zone=req_limit burst=50 nodelay;
```

能够有效降低恶意请求造成的影响。

# 如何判断是否正在遭受攻击？

如果服务器出现以下情况，需要提高警惕：

## 内存持续增长

查看：

```
free -h
```

或者：

```
htop
```

发现 NGINX 内存占用异常增加。

---

## HTTP/2 连接数量异常

查看：

```
ss -tan | grep 443
```

或者：

```
netstat -ant
```

发现大量 HTTP/2 长连接。

---

## 系统日志异常

检查：

```
tail -f /var/log/nginx/error.log
```

重点关注：

```
worker process exited
out of memory
connection reset
```

等异常信息。

# 安全建议

对于生产环境，建议建立以下维护习惯：

- 
定期检查安全公告

- 
及时更新 NGINX

- 
及时更新系统补丁

- 
开启连接限制

- 
开启请求限速

- 
定期监控内存占用

- 
定期检查异常连接

很多安全事件并不是因为攻击手段有多复杂，而是因为系统长期未维护。

保持软件更新，往往是成本最低且最有效的防护措施。

---

# 总结

CVE-2026-49975（HTTP/2 Bomb）展示了协议层漏洞所带来的风险。

攻击者无需发动大规模 DDoS，也无需突破服务器权限，仅通过构造特殊 HTTP/2 请求，就可能让服务器消耗大量资源并最终失去响应能力。

对于使用 NGINX 的站长和运维人员而言，当前最重要的工作包括：

✅ 检查 NGINX 版本

✅ 安装最新安全补丁

✅ 优化 HTTP/2 配置

✅ 配置连接限制与请求限速

✅ 持续监控服务器资源使用情况

安全从来不是一次性的工作，而是持续维护的过程。及时更新软件和关注安全公告，始终是抵御网络攻击最有效的第一道防线。
